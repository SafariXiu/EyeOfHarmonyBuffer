# 地形结构放置：现状分析 与 大型/超大型结构支持方案

> 状态：**分析稿（待裁决）**。本文只描述现状、量化边界、给出候选方案与代价，不含代码改动。
> 目标：让地形系统后续能放置**大型甚至超大型**的树木 / 结构。
> 交叉引用：`docs/TerrainV2/design.md`（V2 地形链）、代码内「设计冻结 §NNN」注记。

---

## 一、结论先行

现有放置层有**一条硬约束**：**任何特征最多只能写到距离当前区块 ±1 个区块（= 48×48 格）**。
这条约束是"树冠跨区块不被裁掉"的**有意设计**，不是 bug；但它同时决定了：

| 量 | 现状上限 | 出处 |
|---|---|---|
| 单个特征最大水平足迹 | **48×48 格**（超出部分静默丢弃） | `TalosBoundedFeatures.Base.setBlock` dx/dz ∈ [-1,1] |
| 单个特征最大"整块放弃"足迹 | **32×32 格**（`canWriteArea` 半径 ≤15） | `canWriteArea` 同一约束 |
| 树高 | **≈250 格**，且 `topY+3<255` 否则整棵放弃 | `BlueprintTree.generateAt` |
| 结构在已填充区块内的部分 | **一律丢弃**（不报错） | `setBlock` 的 `isTerrainPopulated` 门 |
| 结构在未加载区块内的部分 | **一律丢弃**（不报错） | `setBlock` 的 `chunkExists` 门 |
| 写入成本 | **~30+ 次方块查询/次写入**，逐方块光照重算 + 逐方块发包 | `Chunk.func_150807_a` + `World.func_147451_t` |

所以：**"支持超大结构"不是把某个常量调大就能做到的**，它需要换掉放置层的写入模型。
下面是现状拆解、代价量化、以及四条候选路线。

---

## 二、现状：两条写入路径，能力完全不同

```
世界生成
│
├─【底座】ChunkProviderTalos2.onChunkProvider(chunkX, chunkZ, Block[] blocks, byte[] meta)
│    · 直接写方块数组，无任何范围检查、无光照、无实体
│    · 只画"地形底座"（基岩/岩性/表层/海水）
│    · getIndex(x,y,z) = (x*16+z)*worldHeight + y   ← 只能落在本区块
│    · 未被用于放置树木/结构
│
└─【装饰】ChunkProviderSpaceLakes.populate → BiomeDecoratorSpace.decorate
     · 时间点：provideChunk 已返回、区块已在 3×3 邻域内加载
     · TalosBiomeBase.decorate() 被覆盖为空 → 阻断原版装饰
     · 实际入口：BiomeDecoratorTalos2.decorate()
          ├─ WorldGenYuanShiDoubleConeCluster.generate()   ← 唯一"跨区块确定性"先例
          ├─ WorldGenYuanShiVeinTalos.generate()          ← 走 world.setBlock
          └─ decorateBiomeFeatures() → scatter() → TalosBoundedFeature.generate()
                · 树 / 草 / 花 / 蘑菇 / 仙人掌 / 甘蔗 / 睡莲 / 灌木
                · 水洼 / 巨石 / 倒木 / 地面斑块 / 大石
                · 全部继承 TalosBoundedFeatures.Base
```

**关键事实**：底座路径（`onChunkProvider`）**能写满整个 16×16×256 区块**——它没有范围约束。
但装饰阶段（树与结构真正所在的地方）拿不到那个 `Block[]` 数组，于是自己走 `world.setBlock`，
并为此加上了 ±1 区块的安全闸门。

> 换句话说：**"能不能写"从来不是引擎限制，是放置层为了安全自己加的锁。**

## 三、`TalosBoundedFeatures.Base` —— 病灶清单

所有装饰特征（含两种树）共用的基类。逐条列出它对"大结构"的限制。

### 3.1 写入硬闸门（`setBlock`，:122-162）

```java
int cx = worldX >> 4, cz = worldZ >> 4;
if (dx < -1 || dx > 1 || dz < -1 || dz > 1) return;          // ① 超出 ±1 区块：丢弃
if (!world.getChunkProvider().chunkExists(cx, cz)) return;   // ② 未加载：丢弃
if (邻区块 && neighbor.isTerrainPopulated) return;            // ③ 已填充：丢弃
```

三条都是**静默 `return`**——不抛异常、不记日志、不返回失败。
后果：一个 200 格宽的结构会**生成出一块残缺的形状**，而且没有任何地方能看出来它被裁了。

### 3.2 足迹预检（`canWrite` / `canWriteArea`，:169-199）

`scatter()` 每区块随机撒 `perChunk` 次，每次随机一个 `(lx,lz)`。大特征靠 `canWriteArea(lx,lz,r)`
保证"要么完整要么不做"。但 `canWrite` 与 `setBlock` 同一套 ±1 约束 ⇒ **半径 >15 时恒为 false**。
这就是巨树"密度上不去"的根因（注释 :666-669 已自述）。

### 3.3 逐方块成本（**大结构真正的杀手**）

`setBlock` 每次写入要做：

```
block.getLightOpacity(world, wx, y, wz)                      // 虚拟调用
chunkExists(cx,cz) → getChunkFromChunkCoords(cx,cz)          // 可能两次
world.setBlock(..., flags=2)
  └─ Chunk.func_150807_a()
       ├─ Chunk.getBlock / getBlockMetadata                  （+2 次查询）
       ├─ 旧方块 getLightOpacity                              （+1）
       ├─ 旧方块 breakBlock                                   （服务端）
       ├─ 新方块 getLightOpacity                              （+1）
       ├─ 可能 relightBlock 整列重扫 / generateSkylightMap 全区块
       └─ 新方块 onBlockAdded                                 （服务端）
  └─ World.func_147451_t(x,y,z)        ← **无条件执行，与 flags 无关**
       └─ updateLightByType(Sky) + updateLightByType(Block)
            └─ computeLightValue 逐邻居：canBlockSeeTheSky + getBlock +
               getLightValue + getLightOpacity + 读 6 邻居光照
  └─ markAndNotifyBlock → markBlockForUpdate（flags&2）
```

已核对的源码位置（`build/rfg/minecraft-src`）：

| 行为 | 位置 |
|---|---|
| `setBlock` 无条件调 `func_147451_t` | `World.java:528` |
| `func_147451_t` → 天光 + 方块光各一次重算 | `World.java:3268-3279` |
| `computeLightValue` 每格 1 次 `getLightOpacity` + 6 邻居读 | `World.java:3281-3327` |
| `func_150807_a` 的 heightMap / relight / generateSkylightMap 分支 | `Chunk.java:610-729` |
| `generateSkylightMap` 全区块重扫（已实测在 `onPopulate` 里被调用） | `Chunk.java:267-338` |
| `getHeightValue` 正式语义 = **顶面方块的 y+1**（非"上方空气"） | `Chunk.java:188-191` |

**量级**：保守计 **≥30 次方块级查询 / 每次写入**。一个 20 万方块的结构 ⇒ **600 万次查询** +
20 万次 `markBlockForUpdate`（每次都要判断是否发给客户端）。
这是"大结构会卡死"的核心原因，与 ±1 约束是**两个独立问题**。

### 3.4 高度天花板

- `setBlock` 丢弃 `y<=0 || y>=256`（:123）。
- 世界高度已核实为 **256**：`WorldProviderSpace.getHeight()` 默认 256，
  `WorldProviderTalos2`/`WorldProviderSpaceGS` 均未覆写 ⇒ `world.getActualHeight() == 256`。
  `V2TerrainGen.MC_WORLD_HEIGHT = 256` 与之一致。
- `BlueprintTree` 在 `topY+3 >= 255` 时**整棵放弃**（:689-691）⇒ 巨树会被顶到天花板而不是被截断。

### 3.5 地表判定是"硬编码原版方块白名单"

`isGroundSurface`（:231-238）写死 `grass/dirt/stone/sand/sandstone/gravel/snow/packed_ice/clay/mycelium/hardened_clay/stained_hardened_clay`。
Talos 的表层材质来自 `TalosSurfaceProfile`（`TalosSurfaceRegistry`），一旦 profile 引入新方块，
`isGroundSurface` 不认 ⇒ **结构/巨石/水洼会静默拒绝落点**。目前靠 profile 恰好只用原版方块而没暴露。

### 3.6 没有归属预留，特征互相看不见

`scatter()` 用全局 `rand` 独立撒点，特征之间**没有任何空间索引**。
两个大结构可以整体重叠；大树可以长进巨石里。现在尺寸小所以只是审美问题，尺寸一大就是穿模。

### 3.7 线程安全与分配

`Base` 的 `world/rand/chunk/chunkX/chunkZ` 是**实例字段**，而实例被 `BiomeDecoratorTalos2` 复用
（如 `deadBush`、`mushroom` 等字段，:37-44）。服务端 populate 目前单线程所以没爆，但这是隐患。
`treeFor()`（:133-138）每个群系每次都在 new 对象——每区块数次小分配，量大了就是 GC 压力。

## 四、现存的"跨区块确定性"先例（重要）

`WorldGenYuanShiDoubleConeCluster` 已经解决了同一个问题，而且解法干净：

```
拥有区块 (ownerX, ownerZ)  →  key = hash(seed, ownerX, ownerZ)
                            →  Random(key) 决定该区域是否触发、触发几个簇
                            →  簇的几何是 (seed, owner) 的纯函数
当前区块遍历 ±3 区块的候选 owner（7×7=49 次 map 查表）
                            →  对每个命中的 owner，只放置落在【自己 16×16 内】的切片
```

- **生成顺序无关**：任意区块都能重建同一份几何 ⇒ 无论哪个区块先被 populate，每个区块都会补齐自己那份。
- **不写别的区块** ⇒ 不需要 `chunkExists` 检查，不会触发级联区块生成。
- **代价**：每个区块要重算一遍相交结构的几何（用 `ConcurrentHashMap` 缓存摊薄）。

`KNOWN BUG`：`CACHE` 用 `ownerKey(seed, ownerX, ownerZ)` 做键，而几何是用 `(int) (world.getSeed() & 0x7FFFFFFF)` 算的；
world 重载 / 同进程多存档时键空间不隔离（`CaveWorldState` 的注释明确写了"按 seed 隔离，世界卸载时清空"，这里没有）。

**这是最有价值的既有资产**：它证明了"逐区块切片"模型在本工程里跑得通，
新放置层可以直接把它推广成通用机制。

## 五、候选方案

### 方案 A：确定性归属 + 逐区块切片（推广既有先例）

**机制**
1. 结构由 `Region`（如 512×512 格）拥有；`seed+Region` → 结构清单（位置/朝向/尺寸）。
2. 几何是纯函数：`build(seed, regionId, structureIndex) → 方块列表/包围盒`。
3. 每个区块遍历覆盖它的少数 Region，重建几何，**只写落在自己 16×16 内的那部分**。

**代价/收益**

| | |
|---|---|
| 尺寸上限 | **无**（几何可任意大） |
| 生成顺序无关 | ✅ 天然成立 |
| 确定性 | ✅ 同 seed 同世界 |
| 编码量 | 中 |
| 性能 | 每区块 O(相交结构数 × 几何重建)；需缓存，超大结构重建成本高 |
| 主要风险 | 相邻 Region 的结构互相重叠；跨 Region 的巨型结构需要额外"装配"层 |

### 方案 B：整体放置 + 跨区块写入（放开闸门）

**机制**：锚点区块一次性写完整个结构，允许写更远的**已加载**区块。

| | |
|---|---|
| 尺寸上限 | 受"已加载范围"限制（实际 ≈ ±1 区块仍可，更大则取决于加载状态） |
| 生成顺序无关 | ❌ 后生成的区块看到的结构残缺 |
| 确定性 | ❌ 依赖加载顺序 ⇒ 同 seed 不同结果 |
| 编码量 | 小 |
| 主要风险 | 结构残缺不可复现；写已填充区块会诱发方块更新风暴 |

**评价**：只是把 bug 从"静默裁剪"变成"静默不可复现"，不建议作为主路线。
但对**单次、幂等、由外部触发**的放置（指令 / 建筑工具 / 空间站结构）是正确模型——
`WorldGenTileStructure` 就是这一类，它不受 populate 约束。

### 方案 C：底座期生成（把结构搬进 `onChunkProvider`）

**机制**：在 `onChunkProvider(chunkX,chunkZ, Block[] blocks, byte[] meta)` 里按归属直接写数组。

| | |
|---|---|
| 尺寸上限 | **16×16×256**（只能写本区块） |
| 生成顺序无关 | ✅（每区块自洽，天然确定性） |
| 写入成本 | **最低**（数组直写，零光照/零发包；光照由 `onPopulate` 统一收尾） |
| 编码量 | 中 |
| 主要风险 | ① 结构必须"每区块自洽"，跨区块连续性要自己保证<br>② 结构无法查询"已生成的树"（装饰尚未运行）⇒ 与树木的先后关系要定义清楚<br>③ 触碰地形生成核心链路，回归风险最高 |

**评价**：性能最好，且**现成的地形生成已经在这么做**。适合"体量巨大但每区块可独立求值"的结构
（巨型岩体、晶簇、遗迹群）。不适合"需要感知地表植被/已有结构"的结构。

### 方案 D：写入批处理层（与 A/B/C 正交，必做）

不管几何怎么算，写入必须去魔法：

1. **按区块分桶**：一次收集 `(chunk, x,y,z, block, meta)`，区块级一次性提交。
2. **heightMap 一次算完**：替代现在逐方块手工抬 heightMap。
3. **绕过 `func_150807_a`**：直接经 `ExtendedBlockStorage.func_150818_a(x,y&15,z,block)` 写存储，
   避开 `breakBlock`/`onBlockAdded`/relight/发包。
4. **区块末尾一次性补光**：复用 `onPopulate` 已调用的 `chunk.generateSkylightMap()` + `func_150809_p()`，
   跨区块光照交给 1.7.10 延迟补光队列。
5. **预算与统计**：每区块写入上限、每类特征尝试/成功/失败计数，供 `/talosmap` 一类指令输出。

> 注意：`World.func_147451_t` 对**任何** `setBlock` 都执行，`flags` 管不到它。
> 所以"减少写入次数"是唯一的出路，`flags` 调参解决不了大结构的卡顿。

### 方案对比矩阵

| 维度 | A 切片 | B 跨区块 | C 底座期 | D 批处理 |
|---|---|---|---|---|
| 尺寸上限 | 无 | 受加载范围 | 16×16×256 | —（正交） |
| 生成顺序无关 | ✅ | ❌ | ✅ | — |
| 确定性 | ✅ | ❌ | ✅ | — |
| 跨区块连续 | ✅ | ✅ | 需自证 | — |
| 与既有资产关系 | 直接推广 | 新建 | 复用底座路径 | 改造 `Base` |
| 写入成本 | 中 | 高 | **最低** | **最低** |
| 改动范围 | 中 | 小 | 中（核心链路） | 中 |
| 回归风险 | 中 | 高 | **高** | 中 |

**倾向**：`A` 作为几何/归属骨架（有先例、确定性最强），`D` 作为写入层（大结构的前提），
`C` 留给"体量极大 + 每区块可独立求值"的结构，`B` 只用于外部触发的单次放置。

## 六、落地顺序建议（每步可独立验证）

> 原则：先解锁，再加尺寸，最后做效果。每步都能单独编译 + 进游戏看效果。

- **T1 · 写入层（方案 D）**
  把 `Base.setBlock` 换成批处理：收集 → 区块级提交 → 末尾补光。
  验收：现有树/草/花外观**逐位不变**，区块生成耗时下降。
  风险：低（行为等价改造）。

- **T2 · 归属与切片骨架（方案 A）**
  抽出 `StructurePlacement`（归属 / 切片 / 纯函数几何）+ `StructureRegistry`（按群系/区域注册）。
  把 `WorldGenYuanShiDoubleConeCluster` 迁进来当第一个用户。
  验收：晶簇外观不变；顺带修掉 `CACHE` 的 seed 隔离问题。

- **T3 · 树木迁移（含跨区块大冠 / 超高树干）**
  `TreeBlueprint` 保留调参方式，改走 T2 骨架；解除 `canWriteArea` 半径门与 `topY+3<255` 限制。
  验收：巨树能跨区块完整生成；原有 13 种群系树木外观不变。

- **T4 · 大结构作者友好层**
  ① 地形自适应（足迹采样高度/水体/群系 + 可选填平/削坡）；
  ② 空间预留（结构之间不重叠）；
  ③ `isGroundSurface` 改为由 `TalosSurfaceProfile` 提供，去掉硬编码白名单。
  验收：200+ 格宽结构不会一半悬空/一半埋山；不在树干上生成。

- **T5 · 既有装饰特征收口**
  `Pond`/`Rock`/`Boulder`/`FallenLog`/`GroundPatch` 搬到新框架，删掉各自重复的跨区块与地表判定。

- **T6 · 超大型结构（如果需要）**
  在 A 之上加"构件分块装配"：巨型结构拆成若干有归属的构件，各自按 T1~T4 的路径分片。
  这一步只在确有需求时做——它的复杂度**不该**提前付。

## 七、待裁决问题

1. **目标尺寸**：现实目标是多少？（树 50~150 格高？结构 100 格宽？还是"整片区域级"的 1000+ 格？）
   这决定是否真需要 T6。
2. **是否需要自然生成**：超大型结构是走世界生成，还是指令/建筑工具放置？
   （外部放置用方案 B，且不需要碰装饰层。）
3. **是否允许结构改动已生成的地形**：填平/削坡会改写底座，影响 `TalosSurfaceProfile` 的表层材质与后续装饰。
4. **是否接受"整块放弃"策略**：现在大树靠整块放弃避免半棵；尺寸变大后放弃率会上升。
   替代是"局部自适应"（缺地形就削掉那部分枝干）。
5. **性能预算**：目标是什么？（如"任意区块 populate ≤ 5 ms"）

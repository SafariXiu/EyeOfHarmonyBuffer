## 0. 【2026-09】目录搬家 + 极地三件套定案

### 0.1 目录：**守卫入库，考古留本地**（收窄过一次，见下方"为什么不是全入库"）

| | 位置 | 在版本控制里？ | 内容 |
|---|---|---|---|
| **守卫 + 出图工具** | `tools/talos-probe/` | **是，24 个文件 / 238 KB** | 3 个脚本 + `README.md` + `COVERAGE.md` + `_baseline_src_sha256.txt` + **18 个探针** |
| **考古层** | `build/eoh_probe/mtn/probe/` | 否，**206 个文件 / 1130 KB** | 历史上的一次性诊断探针 |
| **暂存区** | `build/eoh_probe/mtn/` | 否 | 拷贝来的 `com/**`、`out/`、`*_report.txt`、`maps/` |

入库的 18 个探针 = **4 道当前不变量守卫**（P215 契约 / P220 单链唯一性 / P221 海洋指纹 /
P233 阻断剖面 / P235 极地验收）+ 2 个出图与数值工具（P237 / P238）+
**`precheck.ps1` 的 FINGERPRINT 表点名的"最强证据"探针**（P168/P169/P170/P172/P176/
P195/P200/P205/P209/P214/P216）—— 那些是每个源文件"结论可复现"的唯一凭据，不能丢。

原因：`build/` 与 `run/` 都在 .gitignore 里，探针工作区原来整个在那下面 —— **清一次 build 就等于
把全部证据销毁**，历史上任何一个结论都无法复现。`.gitignore` 为此加了一条显式豁免：
`!tools/talos-probe/*.bat`（因为有一条 `*.bat`）。

**为什么不是全入库**：全量是 231 文件 / 1.38 MB，其中 95 个探针不到 4 KB、最大的 35 KB，
绝大多数是"当年为了回答一个问题写一次"的诊断；它们进 GitHub 只是把文件列表撑长 10 倍，
换不来可复现性（真正的凭据是 FINGERPRINT 点名的那批 + 守卫里的定义值）。
所以：**能被未来的自己重新跑一遍的进库，只服务于当时那一问的留在本地。**

**这次收窄顺带修掉一个真毛病**：旧 `runprobe4.bat` 只编译**当前要跑的那一个探针**
（`echo probe\%1.java >> srcs.txt`），所以 217 个探针里任何一个腐烂都不会被发现 ——
直到你正好要跑它。极地重构时 5 个 ICE_BAND 时代的探针就是这样把**每一次运行**都搞挂的
（因为当时它们和别的探针在同一目录、被一起编译……现象一样，成因不同）。
现在的规则：

- **入库的 18 个每次都整体编译** ⇒ 守卫集永远不会悄悄腐烂（跑任何守卫都会先证明这一点）；
- **考古层只编译你点名的那一个** ⇒ 206 个历史探针里任何一个腐烂都影响不到守卫；
- 探针不存在时报 `PROBE_NOT_FOUND <名字>` 并以 4 退出。

`sync_check.ps1` 现在还多管一件事：把 29 个"探针可见文件"的 SHA256 与
`_baseline_src_sha256.txt` 对比，漂移就报 `SRC_DRIFT <文件> <旧8位> -> <新8位>`。
**只报不拦**（改 src 是常态，会拦人的守卫一天就会被绕过）。刷新：`sync_check.ps1 -WriteBaseline`。
这份基线的意义是回答"这个定义值是哪一版量出来的、当时还一起动了什么"。

### 0.2 极地三件套：唯一口径 `PolarZone`

用户定案（2026-09）：冰盖缩到 bandD 0.90，芯:浮冰 = 40:60，两极翼各自完整封死，硬墙，
急流 0.35 m/s 注入 `fu/fv`，加冰缘噪声但**面积不变**，热力带一起做。

| 环节 | 落地位置 | 说明 |
|---|---|---|
| 实心冰盖（强制成陆） | `NoiseContinentGrid.landResidual` | `be > CORE_BAND(0.96)` 抬高残差 |
| **浮冰带强制成海** | 同上 | `floeSeaWeight` 梯形权重把残差压低 |
| 浮冰方块 | `ChunkProviderTalos2.fillSeaColumnV2` | 浮冰带海面铺 `Blocks.ice` |
| 虚拟墙掩码 | `RelaxedClimate`(建) → `BarotropicGyre.solve`(用) | `boolean[] wallF`，**不写进 `d.land`** |
| 固定纬向急流 | `RelaxedClimate.updateFlow` | 只读叠加 `fu += jetU(rawBand)` |
| 极地冷带 | `ThermalForcing.baseTeq` | 浮冰区 SST 目标压到 −1 |
| 验收出图 | `CommandTalosMap` 的 `/talosmap polar` | 唯一能看到虚拟墙的地方 |

**两个必须记住的设计事实（都是实测教训）：**
1. **大陆不认纬度。** 冰盖阈值从 0.82 收到 0.96 之后，bandD 0.88~0.92 在很多经度上**本来就是陆地**
   （实测 tileX=0 那一窗自然陆占比 100%）⇒ 浮冰带/极地环流/虚拟墙**没有水可谈**（P236：墙加了，
   但粗网格上新增挡住的海格是 0，RMS 只动到小数点后第 6 位，一度被误判成"墙没生效"）。
   ⇒ 浮冰带必须**强制成海**，极地海盆才是设计出来的东西而不是噪声的运气。
2. **冰缘噪声必须是"整体平移"，不是"给阈值加噪声"。** 早先写 `be = bandD + A·noise(x,z)`：
   噪声在 z 上的梯度与 bandD 同量级 ⇒ 等值线局部不再单调 ⇒ 冰盖裂成几段、面积摆动
   **+27.6% / −13.6%**（P235 实测）。现在 `band(x,z) = rawBand(z − shift(x))`，`shift` 只依赖 x、
   零均值 ⇒ rawBand 对 z 严格单调（每条带每列都是一段连续区间，不可能有洞），
   平移不改带宽 ⇒ **面积按构造守恒**。实测跨度 −6.6k~+4.7k block（±9km 蜿蜒）。

**虚拟墙为什么需要"保守粗化"**（`BarotropicGyre.Lv.wall`）：墙只有 4 个窗口行 ≈ 2.1 个求解器格，
按历史判据（4 个子格 ≥2 个是陆）粗化会在第 2 层整条消失，粗层校正于是能穿墙。
现在墙走"命中任意子格即整格"，天然陆地仍走原判据 —— 后者保证 `wallF=null` 的调用点**逐位不变**。

**P233 为什么不该把虚拟墙算进去**：本表的"贯通墙"是**经向屏障**（一列在整个带上都是障碍 ⇒
水不能沿 X 直穿）；虚拟墙是**纬向屏障**（一圈闭合带 ⇒ 水不能沿 Z 穿进极地海盆），两者正交。
把一个 20km 厚的纬向墙塞进"整带都是障碍"的判据里，永远不可能成立。
虚拟墙的隔绝性由 **P235 的洪水填充**负责，那才是对的那把尺子。

三条实打实的结论：

1. **生产完全不受影响。** `sample()` 只读 `(x,z)` 所属的那**一个**瓦片（halo 是瓦片内 1 格，不跨瓦片），

### 0.7 【2026-09】浮冰带的"护城河"：把强制改成偏置（`FLOE_SEA_FORCE` 1.5 → 0.20）

**现象**：用户看 `/talosmap land` 发现浮冰带像一条笔直的海道把陆地和冰盖切开。
**机制**：`landResidual` 里浮冰带是**强制成海**，强度沿用冰盖的 `ICE_FORCE=1.5` —— 那个量级压得过任何大陆。
P240 逐行实测（x ∈ ±500km、800 列）：bandD 0.91~0.93 的自然陆占比是 48~60%，加规则后变成 **0%**。
⇒ 一条**横贯全图、笔直的 15~20km 洋面腰带**，加上 0.98~0.99 凭空造出的 74~100% 陆地（冰盖）。

**这是设计失误，不是渲染 bug**：它和用户最早嫌弃的"完美纬线圈冰盖"是同一类丑 —— 我只是把完美的陆圈
换成了完美的海圈。根因是**把两个本该独立的旋钮绑成了一个**：冰盖"必须成陆"要强制，浮冰带"成海"
只该是偏置。现在拆成 `ICE_FORCE`（冰盖）与 `FLOE_SEA_FORCE`（浮冰带）两个独立量。

**取舍表（P240 扫出来的，注意 0.45 以上没有中间态）**：

| 强度 | 浮冰带平均陆% (自然≈45) | 0.91~0.93 最长连续洋面 | 判读 |
|---|---|---|---|
| 1.50（原） | 7.4% | 1000 km | 横贯全图 = 护城河 |
| 0.45 | 10.4% | 1000 km | 仍然横贯全图 |
| 0.30 | 14.5% | 678 km | **断崖**：水道断成两段 |
| **0.20（现行）** | **18.6%** | **668 km** | 定案：观感自然，仍保留长水道 |
| 0.10 | 30.7% | 299 km | 分段海 |
| 0.00 | 44.7% | 221 km | 最自然，但退回"某些纬线 100% 是陆、墙等于没加"（P236 的坑） |

**改完的验证（位移半径极小且完全可解释）**：
- P235 仍 `POLAR_STATUS=PASS`：浮冰带海格 2756 → **2519**，墙仍然 **0 泄漏**（细网格与求解器粗网格两级洪水填充都是 0）；
- P169：`mountain.*` 12 条 + `landform.*` 2 条**逐位不变**，**只有 `biome.*` 13 条变了** —— 正是"只动了 0.90~0.96 那一条纬带的陆海"该有的样子；
- P221：海格 38682 → 38445、u 0.29645 → 0.29733、风 0.915341 → 0.918296；
  **闭合盆 0.01882/0.03691 仍然逐位不变** ⇒ 求解器核心一个字节没动。

### 0.8 【2026-09 定案】彻底停止极地地形强制 —— 极地系统对地形的影响 = 0

§0.7 把强制从 1.5 降到 0.20，用户进游戏再看仍然觉得「大陆夹着极点」。于是把**真实海陆**摊开
（P240 逐行，x ∈ ±250km）—— 发现降强度**根本没解决问题**：

| bandD | 自然陆% | 强制后 | 后果 |
|---|---|---|---|
| 0.88 | **100.0%** | 100.0% | 横贯 500km 的完整大陆 |
| 0.91 | 91.0% | 41.8% | 从大陆上凿掉一半 |
| 0.92 | **98.5%** | 27.8% | **凿掉七成** ← 用户看到的护城河 |
| 0.96 | **0.0%** | 33.8% | 凭空造陆 |
| 0.99 | 19.3% | **100.0%** | **凭空造出横贯 500km 的陆地** |

**那一段经度上 bandD 0.87~0.93 天然就是 81~100% 的陆地** ⇒ 任何「在这里放一片极地海」的做法
都只能从大陆上凿水道；**0.96~1.00 天然是海** ⇒ 任何「在这里放一块冰盖」的做法都只能凭空造陆地。
两者一夹 = 用户说的「大陆夹着极点」。**只要强制，就永远是这个形状。**

**定案：把地形强制整个删掉。** 删掉的东西：`PolarZone.ICE_FORCE`、`FLOE_SEA_FORCE`、
`floeSeaWeight`，以及 `NoiseContinentGrid.landResidual` 里的全部极地项
（它现在就是「纯噪声阈值判定」）。`isFloeOcean` 改名 `isFloeBand`（带里有陆地是正常的）。

**极地系统现在只剩四件互不干涉的事，一件也不改地形**：
虚拟墙（求解器掩码，地形上看不出任何东西）· 极地冷带（只改温度）· 固定纬向急流（只读叠加在流场上，
且只在真正的海上）· 浮冰（只在真正的海上铺方块）。

### 0.10 【2026-09】急流搬进水道 ⇒ **环极流第一次真正连续**

### 0.11 【2026-09】沿岸环流落地：把 §0.10 的两个待决点一次解决

**关键一步是想清楚「不用除以 |∇d|」。** 取

```
F = f(d) · (∂d/∂z, −∂d/∂x)             // d = 海岸距离；把 ∇d 旋转 −90° 再乘速度剖面
∇·F = f'(d)·(d_x·d_z − d_z·d_x) ≡ 0    // 对**任意** f 恒成立
```

这一下同时解决两件事：① **严格无散度**（不要求 f 线性、不要求 d 是精确欧氏距离）；
② **窄水道脊线上 ∇d → 0 时场自动归零** —— 那里根本不需要定义切向，因为流速本来就该是 0
（两侧岸的影响互相抵消）。**「切向无定义」那个坑不需要打补丁，它自己消失了。**

方向取「绕陆块顺时针 / 海盆内逆时针」（`COAST_CURRENT_SIGN`，一个数整体反向）。
纬度门依赖 z 会带来**唯一一处残余散度** `−gate'(z)·f(d)·d_x ≈ 7.5e-6 s⁻¹`，只出现在 20km 宽的
一条纬带上，已记录。

**与水道急流不打架**：`COAST_CURRENT_INNER = 30km` 以内不给沿岸环流，而水道最宽处仅 ~26km
⇒ 水道里只有那条急流（否则会变成两岸反向的剪切流）。

**P235 新增 [3d]：剖面 + 无散度的单元测试**（平面距离场 |∇d|=1、非线性 f 实测）：

```
f(d): 10k=0.000  30k=0.000  40k=0.053  55k=0.150  80k=0.105  120k=0.059  200k=0.019
无散度测试：max|∇·F| = 1.613e-10 s⁻¹（max|F| = 0.149 m/s）⇒ 浮点噪声量级
```

**实测剖面（x=0）—— 结果恰好是真实南大洋的结构**：

| bandD | u | 是什么 |
|---|---|---|
| 0.77 | +0.0232 | 沿岸环流（门在 0.76~0.80 平滑升起） |
| 0.79~0.82 | **−0.116 / −0.149 / −0.135 / −0.098** | **向西的沿岸流** |
| 0.84~0.89 | +0.065 → **+0.3367** → +0.063 | **向东的环极急流**（u−jet ≈ −0.0015） |

**向东的急流紧挨着一条向西的沿岸流** —— 这正是真实南大洋：ACC 向东，而贴着南极大陆的
**南极沿岸流（东风漂流）向西**。地转上的巧合，但是个很好的兆头。

**验证**：P215 `20/20` · P220 `12/0` · P221 `PASS` · P235 `PASS` · P240 `PASS`；

### 0.12 【2026-09】水道收窄 + 墙归位：把那个旋钮拧回去

## 1. 【最重要】"测的是旧代码"陷阱 + sync_check.ps1 守卫

`runprobe4.bat` 从 `src` 往探针树里拷的是**逐个文件的列表**，而 javac 会把探针树里的
`com\*.java` **整体**编译。任何"探针树里存在、但不在拷贝列表里"的文件都会**静默地停在旧版本**。

**已经踩过三次：**
1. `RelaxedClimate.java` —— isLandCell 修复**明明改了**，验收却显示"完全无效"（数字与修复前一模一样）。
   真相：拷贝列表里根本没有这个文件，测的是旧副本。
2. `PeriodicNoise.java` / `MountainLayerV2.java` —— 差点让批次 1.1/1.2 的"指纹逐位相同"落空
   （MountainLayerV2 正是 P169 的指纹对象，用旧副本验证等于没验证）。

**现在的做法：**
- 拷贝列表已补齐到探针实际用到的全部 worldgen 文件；
- `runprobe4.bat` **每次运行前先跑 `sync_check.ps1`**，任何不一致 → 打印 `STALE_COPY <相对路径>` 并
  `exit /b 2`，**探针根本不会启动**。宁可跑不起来，也不要跑出"看起来正常"的错数。
- 守卫本身做过负向自测：故意改脏一份副本 → 报 `stale 1` 并返回 1；恢复后 → `stale 0` 返回 0。

**为什么不能改成"整目录拷贝"（已评估，结论：不可行）：**
探针树**有意**只编译 src 的一个小子集 —— 其余文件依赖 GTNH/Minecraft 类型，不在探针 classpath 上；
而且探针树里还有**手工桩**（`Config\TalosConfig.java`、`probeorig\OrigMountainV2.java`）在 src 里不存在。
整树拷贝会让 javac 直接失败。
⇒ 正确做法是**保持最小拷贝列表 + 用脚本证明列表是完整的**。

**改了 src 里任何一个探针会编译到的文件之后：** 直接跑探针即可（bat 会拷贝并先自检）；
若 sync_check 报 STALE_COPY，把该文件加进 bat 的拷贝列表（或手工 Copy-Item 一次）。

**第二道守卫（本批新增，见 §9.3）**：`precheck.ps1` 会做**反向**核对 —— *探针树里的每个文件是否都在拷贝列表里*。
这一类问题 sync_check **结构上不可能发现**（它只比对两棵树都有的文件）：文件当时与 src 完全相同，
于是守卫报 `in-sync 27; stale 0`，看起来完全健康，但任何人改一次 src 就会静默留在旧版本。
本批实测到 4 个这样的文件并已补齐列表。

## 2. 采样顺序：必须 tile 主序，且【先估工作集】

三次"进程跑飞"（P140 27min / P190 ~100min / P191 >50min）的共同成因：
**采样顺序在瓦片间跳跃 → 工作集 > 缓存容量 → 每一步都在重建刚被逐出的那块。**

- `CACHE_LIMIT`（气候窗口）= 16；单行工作集含 TILE_BLEND 的 ±1 瓦片 ⇒ 5，Z 方向 3 ⇒ 最坏 15。
- 取样务必写成：**外层 tileX/tileZ，内层该瓦片内的列与行**。
- **第 4 次跑飞（P209 的 period 段）**：`kind(x,z)` 与 `kind(x,z+200000)` 逐对交替查 → z 上每步跳 200km，
  而 LandformField/V2BiomeField/MountainLayerV2 的 **Z 瓦片高只有 50km** ⇒ 每步跨 4 个瓦片。
  结果 **6,000 次采样触发 7,165 次 MountainLayerV2 求解（≈1.19 次/查询）**，1,110 s CPU 跑不出来。
  改写成**两趟连续扫描**（z 升序各扫一遍再比较）后秒级完成。
- **动手前先估工作集**；探针里设 `RelaxedClimate.BUILD_HARD_CAP`（默认 0 = 不限），
  超限会**快速失败并报出计数/缓存占用/当前 tile**，比闷跑一小时后被杀好得多。

## 3. 哨兵纪律：凡判据，必配一个【必须为 0】的对照

最有效的一招。例：isLandCell 修复后残留 2.95% 不一致，光看这个数字只能说"大概还剩点问题"。
加一个对照：**把查询点对齐到网格正中心**（此时掩码值就是真值）→ **0.0000%（0/172800）**。
于是结论从"残留 2.95%，大概是海岸线"变成硬结论：**残留全是 5km 的 z 量化，是掩码分辨率的内含代价，不是 bug**。

用法：任何"修复是否生效""仪器是否可信"的判断，都配一个理论上必须为 0（或必须逐位相同）的对照。
负对照组合同样重要：P210 里"海区不碰 Y 接缝"时开/关 WRAP_Y 必须**逐位相同** —— 它同时验证了开关本身。

## 8. 已知的行为变更及其【用户可见影响】

### isLandCell 修复（`RelaxedClimate.isLandCell`，本轮唯一面向玩法的行为变化）

**一句话影响面**：**海岸带陆地的「湿度 / 群系」会变，温度不变**；变化量与旧版本相比可达
`moist ±0.2 ~ ±0.44`（湿度坐标中位约 0.45，所以**足以推动群系边界**）。

**机制（为什么只影响湿度）**：
- 唯一消费 `sampleSst` 的玩法路径是 `ClimateCoords` 第 115-124 行：
  陆格 → 沿**上风方向 15km**（`SST_OFFSET`）取一点 → 若该点是真海面，则
  `moist += SST_GAIN(0.90) × (sst − sstExpectation(bandD))`。
- **`c.temp` 全程不接触 SST**（第 131 行只用 `temp − LAPSE × 高度`）⇒ **温度不变**。
- `GlobalClimate.sample` 也用 `sampleSst`，但它用**逐点真值**做门（第 47 行 `isLand ? NaN : ...`），
  且其 sst 字段没有玩法消费者 ⇒ 对本条无补充影响。

**受影响的地理范围**：
- 不是只有极区。修复前"真海面被判成陆 → NaN"的比例**散布在赤道→极地全程**（P191 原表：
  z=102km 72.8%、302km 68.3%、402km 84.3%、602km 32.5%、702km 62.5%、2km 35.3%）；
- 但对**玩法**真正生效的只有：**上风 15km 内是海面的那圈陆地**；
- 量级举例（用修复后的实测值算）：
  - z≈104km（副热带）：该带真海格 SST 0.595~0.986（均值 0.846），`sstExpectation(0.204)≈0.358`
    ⇒ 距平 **+0.49** ⇒ `moist +0.44`；
  - z≈404km（亚寒带）：真海格 SST −0.571~−0.300（均值 −0.431），`sstExpectation(0.804)≈−0.230`
    ⇒ 距平 **−0.20** ⇒ `moist −0.18`。

**给玩家的说法**：**走进新生成的海岸带时，沿海的湿度与群系分布会和旧版本不同**
（海岸林/草原/荒漠的边界推移），**温度不带这个变化**。已生成的区块不受影响（只影响新生成的地形）。

### 9.2 哨兵：证明断言不是恒真、也不是恒假

- **P215 段 B（反向哨兵）**：进程内把 `WRAP_Y` 置 false ⇒ 期望 **17/17 全绿**；
  恢复后整张表与段 A **逐位一致**。⇒ T4a/T4b **既能红也能绿**，段 A 的失败不是"永远失败"的装饰。
  末行 `SENTINEL_STATUS=PASS`。用运行时注入而不是"改文件再改回来"：不留脏树（脏文件正是
  "测的是旧代码"事故的来源）。

### 9.3 precheck.ps1（双向核对 + 覆盖审计）

真正导致结论作废的 `STALE_COPY` 仍由 `sync_check` 硬拦（`exit /b 2`）。

    并用"临时注释掉一行 → 报 `COPYLIST_GAP` → 恢复（bat 的 SHA-256 逐位还原）"做过负向自测。
- **覆盖审计**：`-Table` 打印 28 行全表；`-WriteTable` 生成 `COVERAGE.md`

  - `dir=` 探针**点名**它；`trans=` 探针能通过调用图**到达**它。

## 10. 批次 1：两处"同源缺陷"的根治（缓存键截断 + 跨线程共享的可变上限）【本批新增】

本批只做两件事，都是**零行为变化**的结构性修复：不改变任何已生成世界的数值，
只消除"同一份逻辑抄了 N 份"和"一个进程里两个线程改同一个静态字段"这两种缺陷形态。

### 10.1 缓存键：4 份拷贝 → `util.WindowKey`（唯一实现）

原来 4 个层各写了一份同样的位段打包（`RelaxedClimate.cacheKey`、`LandformField.tileKey`、
`MountainLayerV2.cellKey`、`V2BiomeField.tileKey`）：

    ((long) seed << 40) ^ ((long) (a & 0xFFFFF) << 20) ^ (b & 0xFFFFFL)

**缺陷**：`seed` 是 int（32 位），左移 40 位后**只有低 24 位留在 long 里**，高 8 位被静默丢弃
⇒ `seed` 与 `seed + 2^24 (= +16,777,216)` 的两个**不同世界共用同一批已解窗口**
（玩法表现："换了种子，地形/气候没换"）。瓦片侧另有 `& 0xFFFFF` 掩码，
`a` 与 `a ± 2^20` 同键（真实定义域 |tile| ≤ 6000，暂时碰不到，但这是一颗埋着的雷）。

**现在**：`WindowKey.of(seed, a, b)`，三个 int 的**全部 32 位**都参与混合，且**可证明单射**
（三个 `x ^= x>>>k` 与"乘奇数模 2^64"都是双射，由外向内逐层反推字段唯一）。
不做位移打包的理由是算术性的：32+20+20 = 72 位 > 64 位，**任何"各占一段"的打包都必然丢信息**。

**实测（`TalosContract` T6a）**：48,223 个键（7 种子 × 83×83 瓦片，含 `1` 与 `1+2^24`、
`0` 与 `±2^20` 这些精确的别名点）⇒ `WindowKey.of` **碰撞 = 0**；
同一批样本用旧公式跑 ⇒ **碰撞 = 21,979**。后者是**反向对照**：它证明这一行**能红**，
不是恒真的装饰品。（第一次跑报 3549 个"碰撞"，原因是我自己的取样表把 `0/±1` 去重漏了
—— 同一个 `(seed,a,b)` 被插了两次。**先查仪器，再改被测对象**。）

同时删掉一对靠位段**反解**坐标的死代码（`RelaxedClimate.decodeTileX/decodeTileZ`，零引用）：
键的位模式没有语义，不允许存在第二个"键 ↔ 坐标"的解释。

### 10.2 步数上限：`BarotropicGyre.STEP_CAP` 静态字段 → `solve()` 的显式参数

原来 `RelaxedClimate` 的外层耦合循环这样用：

    BarotropicGyre.STEP_CAP = 416;  updateFlow(...);  BarotropicGyre.STEP_CAP = 0;

而 `RelaxedClimate.warm()` 会把**窗口构建丢到 `HEATER` 线程池**（预热），
预热线程同样调用 `solve()` —— 于是**同一个 (种子, 窗口) 的解取决于另一个线程当时停在外层第几轮**：
前台/后台谁先跑完就得到不同的流场，并被写进窗口缓存**长期生效**。
这是真正的**非确定性世界内容**缺陷，不是理论风险。

**现在**：`solve(..., int stepCap)` 是显式参数（旧的 11 参重载保留给历史探针，= `stepCap 0`），
调用点的上限在**它自己的栈帧**里，结构上不可能再串。`TalosContract` **T6b** 用反射守着这条：
`BarotropicGyre` 上**不存在** `STEP_CAP` 字段，且存在 `public static solve(..., int stepCap)`。
纪律靠"结构上做不到"守住，不靠注释。

**顺带**：`P202` / `P207` 只在 `say(...)` 里打印过这个字段，已改成打印"显式参数"；
它们的**归档报告**（`p202_report.txt` / `p207_report.txt`）保留原样，别拿它们跟新跑的输出逐字对比。

### 10.3 `P215` 的判据从"全绿"改成【已声明缺陷清单】

段 B1（运行时把 `WRAP_Y` 置 false）原来的判据是"失败数必须变成 0"。本批多了 T6 两行之后，
这个判据会**因为一条与 WRAP_Y 无关的行**而误报。现在改成两段式：

- 段 A：失败集合必须**恰好**等于 `DECLARED_DEFECTS`（现在 = `{T4a, T4b}`）。
  多一条失败 = 未登记的缺陷 → 报错；清单里有一条其实**不失败** = 登记过期（修好了没删）→ 也报错。
- 段 B1：`T4a/T4b` 必须转绿，且**其余行的失败集合必须与段 A 完全相同**。

于是"哨兵证明断言能红能绿"这件事**不依赖当前有几条缺陷**：`WRAP_Y` 修好那天只需从
`DECLARED_DEFECTS` 里删掉两行，探针不会因此变成必须改判据的负担。
